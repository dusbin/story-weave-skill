# 设计说明

为什么是这个结构。**取舍的理由比结构本身重要**——结构可以改，理由不该丢。

---

## 一、三步流水线，为什么每步都落盘

```
输入文本 ──sw analyze──→ analysis.json    看清原文 + 演绎思路（含"哪些还不确定"）
              ↓
          sw plan ──────→ plan.json        演绎方案 + 修改点 + 硬约束（状态：待确认）
              ↓
          sw confirm ───→ plan.json        人工确认结果写回（状态：已确认）
              ↓
          sw weave ─────→ prompts.md       逐节写作指令（注入硬约束 + 常识自查表）
              ↓（模型/人写草稿）
          sw weave ─────→ story.json       正文组装
              ↓
          sw check ─────→ check.json       常识校验报告
              ↓
          sw render ────→ md/html/pdf/json
```

每一步的产物都是**文件**，不是内存里的对象。理由有三：

1. **可中断**：分析完可以先看报告，隔天再决定怎么演绎；
2. **可复现**：`story.json` 里记着 `planRef`（方案修订号）与 `analysisRef`（原文指纹），
   事后能确认"这份正文是对着哪一版方案、哪一份原文写出来的"；
3. **可核对**：人工确认的勾选、批注、留痕都在 `plan.json` 里，能被 diff。

## 二、为什么要有"常识标尺"

最初的设计是"所有作品都按现实常识判"。这行不通：

- 仙侠里的轻功不违反任何设定内的规则，但按现实判就是硬伤；
- 反过来，架空世界里的人物**仍然是人**——饿了三天还跑马拉松，照样是硬伤。

所以引入标尺，并明确两件事：

| | 现实向 | 架空向 |
|---|---|---|
| 判定基准 | 现实世界的物理/生理/时间/社会制度 | **作品自己立的规则、代价与限制** |
| 设定本身 | 不适用 | **不算错误** |
| 人物生理 | 照现实判 | **照现实判**（除非明确说明非人） |
| 时间/数量/空间 | 照现实判 | **照现实判**（矛盾永远不是设定自由） |

实现上用 `overridable` 一个字段表达：

- `overridable: true`（会飞、瞬移、复活、超前科技）→ 架空标尺下**降一档**，并提示"要么改文，要么把设定写明"；
- `overridable: false`（人体极限、时间算术、数量矛盾、前后矛盾）→ 照原档判。

**识别策略上刻意保守**：必须有**正面信号**才判架空；没有任何幻想信号时按现实兜底（更严的一侧），
并在报告里说明"若这是架空设定，请用 `--tier speculative` 覆盖"。两类信号都很强时（穿越重生）
判为架空并标记 `conflict`——宁可在架空侧宽松（靠降档兜住），也不要把"他会飞"当硬伤报给作者。

## 三、为什么"演绎"必须区分六种模式

"演绎"是个含糊的词。用户在说"演绎一下这段文字"时，可能想做六件完全不同的事，
而它们对**原文事实的处理方式**截然不同：

| 模式 | 对原文事实的态度 |
|---|---|
| 扩写 | 结局不变，只填中间的空白 |
| 续写 | 原文结尾是起点，往后推 |
| 前传 | 原文事实是**终点**，要倒推出它 |
| 改编 | 明确列出"保留项/替换项"，替换项之外一律照旧 |
| 番外 | 不改变主线事实，但故事自足 |
| 多线推演 | 分叉点之前完全照旧，且**只许差异一个变量** |

不区分模式，就无法定义"什么叫做错了"。所以模式是本技能的一级概念：
每种模式自带**适配度评分**（可解释，不是玄学）、**写作骨架**、**不变量**、**修改点提案**。

## 四、为什么"人工确认"要做成硬闸门

方向性决策的返工成本是非线性的：模式选错 → 骨架、约束、修改点全错 → 正文白写。
所以 `plan.json` 初始为 `pending_confirmation`，`sw weave` 会拒绝并报出具体原因。

确认走两条通路，**都留痕**：

1. `buildConfirmationQuestions()` → `confirm-questions.json`，**就是 `ask_user_question` 的入参格式**，
   用户可以在界面上勾选，不必自己组织语言；
2. `applyConfirmation()` → 把勾选写回 `plan.json`，每条修改点带 `decidedAt`，
   改动记入 `status.history`（含改动**前后**的值）。

只走 1 不落盘，确认过程没有证据；只走 2 则用户要自己打字描述。两者结合才完整。

一个细节：卡片上**未勾选**的修改点按"不改"处理**并记录**，而不是留成 `pending`。
因为 `pending` 会让闸门永远拦着，而"没勾选"本身就是一种决定——把它写下来，比让它悬着诚实。

## 五、为什么常识校验要分"确定性"与"需模型判断"

让 LLM 判"这段有没有常识错误"，会得到两类坏结果：假阴性（没看出来）与
**假阳性（把设定允许的当错误）**。而让引擎判"他为什么突然原谅了她"，它根本判不了。

所以按**可计算性**切开：

- **确定性**（79 条）：把文本里的量解析出来，跟量级表比。
  "三百公里 / 两小时"→ 150 km/h > 人体上限 → 硬伤。可复现、可测试、可 diff。
- **需模型判断**（23 条）：引擎只做两件事——**收窄**（把问题问具体）与**取证**（附上原文与行号），
  判定交给模型/人并留痕。

一条贯穿全库的纪律：**每条判定都必须能指回原文行号**。`normalizeFinding` 会丢弃没有出处的命中——
宁可漏报，也不给出无法核对的指控。同理，模型判 `fail` 时可以指定它实际指的原文，
否则结论会挂在引擎按关键词取的"候选证据"上，作者看了会以为报告张冠李戴。

## 六、为什么"内部设定一致性"要单独实现

架空向作品的硬伤不在现实常识里，而在**作品自己立的规则**里。所以 `internal.mjs` 做三件事：

1. **事实不变性**：原文写死的年龄被改写 → 硬伤。
   判据刻意收窄为"**同一个事件被重述，但值被改了**"：
   - 原文「哥哥十五岁就离开了家」vs 演绎「男性，三十岁上下」→ **不报**（不同时间点，一致）
   - 原文「哥哥十五岁就离开了家」vs 演绎「哥哥十八岁那年离开了家」→ **报**（同一件事，值被改）

   朴素的"出现不同年龄就报"会把第一例判成硬伤，而那是最伤可信度的误报。
2. **设定违反**：从设定句里**推导出被禁止的行为短语**（「灵根残缺者永不可能结成金丹」→「结成金丹」），
   再到正文里找它的**肯定式**出现（否定式如"没能结成金丹"不算违反）。
3. **方案落实**：beat 是否逐节对应、人工确认的修改点是否真的落地、结局倾向是否兑现。

## 七、为什么约束要"向前移"

事后校验只能抓错，抓到的错都要返工。所以 `prompts.md` 里逐节注入了：

- 不可改写的事实（`FACT-001`）
- 作品已立的设定（`SET-001`）
- 演绎不变量（`MODE-001`）
- 人工确认要落实的修改点
- **10 条常识自查表**（时间记账 / 生理极限 / 空间行程 / 信息来源 / 因果关系 /
  时代一致 / 数字一致 / 专业流程 / 架空设定 / 人物一致）

这十条是按"叙事文本最常犯、也最容易被读者抓住"的顺序排的。
动笔前把最容易犯的错误摆在眼前，是成本最低的一道防线。

## 八、分层与依赖

```
scripts/          CLI：参数解析、读写文件、终端输出（唯一允许 IO 的地方）
  _args.mjs       参数解析（未知参数直接报错，不静默忽略）
  _io.mjs         文件读写、输入收集、终端格式化
  sw-*.mjs        各步命令；既能单独运行，也能被 sw.mjs 复用
  sw.mjs          dispatcher + 一键试跑 + 帮助
      ↓
lib/              纯函数（无 IO，可测试）
  text.mjs        切分与定位：括号栈感知的断句、行号映射、指纹
  util.mjs        通用工具（含中文数字解析）
  schema.mjs      四类产物的数据结构契约与校验
  genre.mjs       体裁 / 常识标尺 / 年代识别
  extract.mjs     人物 / 叙事视角 / 时间线 / 地点 / 世界设定 / 事实锚点
  modes.mjs       六种模式：适配度、骨架、不变量、修改点提案
  analyze.mjs     第一步组装（含留白点识别）
  plan.mjs        第二步：方案构建 + 确认状态机
  weave.mjs       第三步：写作指令 + 草稿导入 + 正文组装
  check.mjs       第三步验收：报告组装 + 打分 + 结论
  render.mjs      四类产物 → markdown / json
  terms.mjs       术语表
  commonsense/
    engine.mjs    规则契约与运行器（取证与收窄）
    kit.mjs       规则工具箱（时长/距离/温度/年龄/年份/否定）
    internal.mjs  内部设定一致性 + 事实不变性
    rules/        102 条规则，9 个模块
  export/         HTML 渲染 + Chrome headless PDF（离线，无外部资源）
```

**`lib/**` 里没有 IO**，这让全部逻辑都能用 `node --test` 直接测（461 个单元测试 + 76 项端到端断言）。

## 九、失败时的姿态

| 情况 | 行为 |
|---|---|
| 输入为空 | 报错并提示如何提供输入（`--text` / `--in`） |
| 找不到 Chrome | 只跳过 PDF，写出 md/html/json，并提示如何安装或设 `CHROME_PATH` |
| 体裁证据不足 | 按现实标尺兜底（更严的一侧），并明确说明可覆盖 |
| 年代不明 | 时代错位类检查**整体跳过**（避免误报），并在报告里说明 |
| 解析不出量 | 返回 `null` 并跳过该条判定，绝不猜 |
| 规则自身抛异常 | 记为一条 `minor` 并注明"这是引擎问题，不代表作品有问题"——不让规则缺陷冒充作品缺陷 |
| 方案未确认 | 拒绝演绎，逐条列出未处置的修改点 |
| 草稿未分节 | 警告并说明建议格式，不静默接受 |
| 节数与 beat 不符 | 在 `story.meta.alignment` 显式标出，不藏 |
